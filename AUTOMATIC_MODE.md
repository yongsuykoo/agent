# Automatic maintenance — 0.7.1

Start `windows\ConnectNamed.cmd` once and leave **Automatic maintenance** checked. Enable AI jobs and enter the provider and tunnel keys locally. After starting, leave the helper open and the desktop unlocked. The local automatic cycle works even while this chat is closed; it does not require you to enter test tasks or upload reports.

The cycle scans installed apps every five minutes, waits for 60 seconds without input before a disposable Windows test, and studies up to five apps per day using the existing persistent research queue and budget. AI-enabled tests include generated speech; they do not record your microphone. A successful suite can run twice per worker version/day for repeatability. A failure is saved and suspends repeat testing of that version until a new worker release arrives. Research and tests incur provider charges when AI is enabled. Tests clear Calculator; avoid using the desktop while a test runs. Inactivity is checked before starting a test, not a guarantee that user input during the test is detected.

The connection host checks the project's fixed HTTPS release feed every five minutes. It accepts only artifacts signed by the controller whose public identity is already pinned in `windows/cloud-controller.json`. It checks the checksum, size, package identity, dependency compatibility and a startup preflight before switching. A bad release retains the previous worker and retries later. Updates happen between jobs. The app worker runs in a separate local process; the host retains its relay, pairing key, local credentials and app-control grants. Routine worker fixes therefore do not require another download, Setup.cmd, restart or pairing link. A host/protocol/dependency change can still require a local installation.

The cloud assistant must publish a tested signed release for code repairs. This process does not give the app authority to sign its own generated code or claim a failure was fixed merely because a new version loaded. Publish instructions: run the full suite, build the wheel, run `tools/publish_worker.py` with the existing controller key file outside the repository, stage the public wheel/manifest, and push the tested release. Never commit the private key. The fixed release paths are `downloads/agent-worker.whl` and `downloads/worker-release.json` in `yongsuykoo/agent`.

Progress is saved privately in `%LOCALAPPDATA%\AppAgent\automatic-progress.json`; full test reports stay in the self-tests directory. The cloud can read automatic progress through the existing encrypted learning report. It reports separate host/worker versions through `/info`. No new Cloudflare configuration is required.

Automatic mode lasts up to eight hours while the helper remains open. Manual mode retains the two-hour session. STOP, hotkeys, closing the helper and expiry still cancel work. User-selected app controls remain scoped to their window/process/version and persist through worker updates, not across a stopped session. The automatic cycle does not grant itself controls in arbitrary apps, execute queued hardware/file-transfer plans, or establish universal app mastery.

All 222 cloud regression tests pass; see CORE_TASKS.md for the new task engine checks. The suite exercises actual signed update verification, a real child process, local permission transfer, cancellation, rejection of altered artifacts/dependencies, startup failure fallback, idle gating and persistent failure records. Live Windows update switching and the new automatic cycle still require acceptance on the user's Windows host. Passing these tests does not complete the broader all-app goal.
