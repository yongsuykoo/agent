# Personal task engine — 0.7.1

The Windows app's default automatic mode accepts a submitted goal, chooses from the discovered inventory, and plans one to four ordered app steps. It finds the matching window or launches the discovered Start-menu identity. When several documents match, it attempts to identify a newly opened window instead of arbitrarily choosing an existing document.

Run `windows\Start.cmd` after setup. Leave the window selector on **Automatic — choose app from command**. The visible **Run submitted chat/voice tasks autonomously** option authorizes actions for the submitted task, avoiding repeated action prompts. Uncheck it for supervised operation. Clicking **Push-to-talk** starts recording; finishing recording transcribes and submits the command in autonomous mode. STOP still cancels. The task, inventory names, observed control text and recorded command go to the configured provider; app images are included only with the image option checked.

Example goal: `Calculate 23 plus 19 in Calculator and put the result in Notepad.` The planner selects both app identities. The engine verifies each visible output before proceeding. A later step can refer to the earlier verified output through `{{result:1}}`; references to future or failed results are rejected. Simple requested arithmetic is independently checked with decimal arithmetic, and exact-text requests must retain their original text. The engine does not execute model-supplied shell commands or executable paths.

Documentation and technical references remain useful, but a failed manual lookup no longer automatically prevents an authorized observable operation. The engine can use current accessible controls and saved verified workflows. It records the documentation failure and an observed interface profile; it does not turn missing documentation into a claimed capability. Invalid credentials, provider throttling, cancellation or a changed app generation still stop execution. Tasks have a bounded action count; a stalled or incorrectly verified task can receive one focused documentation recovery attempt. Failed attempts remain in the evidence.

Successful workflows and their verified interfaces are retained per app version in the local catalog. Aggregate records go to local `objective-sessions.jsonl`. `steps_verified` means the planned outputs were independently checked. It is not certification that every part of an arbitrary user's intention, every app feature, or every future scenario has been understood. The model can still choose an incomplete plan for a complex request.

The 0.7.1 cloud suite passes 222 checks, including the real task runner operating two simulated app adapters, recovery retaining a failed attempt, rejected arithmetic, invalid result references, process changes, UI routing, signatures, update validation and cancellation. The packaged-wheel suite repeats these checks in a fresh environment. Native desktop interaction and model replies in these tests are simulated. The new multi-app flow and microphone submission require live Windows acceptance; earlier live Calculator/Notepad evidence does not establish these new paths.

The product currently has a Windows adapter. Programs with custom inaccessible canvases may need the optional screenshot controls or an additional adapter. Unregistered apps, complex dialogs, app-specific output verification, cross-platform adapters and broad repeated live acceptance remain gaps. The engine does not scan all personal browsing history, obtain hidden credentials or infer complete mastery from a software inventory.

The 0.7.1 signed worker keeps protocol 1 and the 0.7.0 minimum connection host. An active compatible helper can receive backend changes between jobs without a new pairing link. The standalone app interface must be launched from the new installation to expose the new task director and voice behavior; worker updates do not replace an already running interface or add new host dependencies.
