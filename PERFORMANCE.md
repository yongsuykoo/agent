# Faster operation and uncapped usage — 0.7.2

The application can operate without a daily usage cap imposed by App Agent. Set **Daily studies/designs (0 = uncapped)** to `0` and choose **Apply / resume** in the main app. New installations default to `0`; existing saved choices remain in place. In the connection helper, **No daily AI study/design cap** selects the same local setting. This removes daily research and experiment-design ceilings. Authorized background practice also removes its daily attempt ceiling when the main app is uncapped. Usage counters remain visible/persistent. These are counts of attempts, not a monetary accounting system or an actual dollar budget.

Cloud reasoning, web search and transcription still use the provider's paid API. Uncapped usage does not make those services free or bypass account credits, quotas or rate limits. Authentication/rate-limit failures stop new research waves and impose the existing 15-minute retry delay. Work already in flight may complete; cancellation prevents its research results from being saved. STOP and existing session expiry remain available. A finite concurrency limit controls resource use, independent of daily usage caps.

Independent app research uses three reader threads by default, configurable from one to four. Each app's source pages are retrieved concurrently, with at most four active document downloads across the process. Results preserve source/citation order. The owning thread claims app research leases, reserves usage atomically and commits documents; network threads never share its SQLite connection or control the desktop. A crash lease expires after 30 minutes, and changed app generations reject old documents. Study batches are finite and continue in later automatic cycles. Deeper study and experiment planning remain sequential within each batch. A batch with a provider failure completes its current wave, then stops before starting another.

Successful accessible workflows can become local routines. They are restricted to the same requested task and current app generation; there is no automatic parameter substitution. Each action rechecks control identities, visible values/states, permission and window/process identity. Each following state and final output must match. Coordinate clicks, visually assessed outcomes, ambiguous controls and oversized routines are excluded. A changed state returns to cloud planning from the actual observed state; a changed window/process or denied permission stops execution. Success always produces fresh execution/verification evidence.

Fully verified multi-app plans are cached against the participating app generations. A repeated task can reuse both plan and routines without cloud calls. Provider construction is deferred, so an eligible local replay can execute without a configured provider key. Unfamiliar tasks, unmatched states, voice transcription and documentation still require the provider. The cloud never receives the complete routine guards as part of a planning hint; those guards remain local.

Windows registry notifications watch available uninstall/AppModel registrations for changes. A change remains pending while the desktop worker is busy and triggers a scan when it becomes available. The five-minute scan remains as reconciliation for missed signals, inaccessible registry keys and software registered through other mechanisms. This is not comprehensive detection of every unregistered executable or a live proof of successful adaptation to an actual installation.

The 0.7.2 cloud suite passes **237 tests**. A real three-thread barrier test verifies parallel app reading; a second verifies concurrent manual retrieval and citation order. The repeated two-app simulation uses five model requests initially and zero on replay, including with unavailable provider credentials. Other checks cover concurrent finite-budget reservations, uncapped counters, leases, provider backoff, cancellation, version invalidation, permission/process changes and failed replay. Desktop/model execution and Windows registry signals are simulated. This measures request elimination in those fixtures, not an established Windows latency speedup or universal app mastery.

The worker release retains protocol 1 and minimum host 0.7.0. Compatible active hosts can load the new backend study/replay logic between jobs. A new main-app launch is needed for the usage/parallel-reader controls. Registry notification wiring and the helper's new local checkbox require the 0.7.2 host/interface installation; worker replacement does not patch the already running parent interface. Older host validation rejects an explicit `daily_limit: 0` request; compatible backend jobs use the locally saved daily setting when present. Local usage choices take precedence over the request's daily setting. No Cloudflare reconfiguration is required.
